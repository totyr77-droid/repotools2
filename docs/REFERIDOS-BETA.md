# Referidos y ranking — exclusivamente beta

## Entrega y aislamiento
Sistema integrado en Ajustes → Referidos, con ranking público y vista administrativa. No pestaña principal nueva ni cambios de Stock/Biblioteca/escáner. Main permanece intacto. El usuario confirmó que Render desarrollo utiliza el proyecto Neon repotools-desarrollo, separado de repotools2. Se comprobó que los endpoints son distintos y se aplicó la migración únicamente a desarrollo. No se ejecutaron pruebas con cuentas reales ni escrituras en producción.

La activación exige REPOTOOLS_REFERRALS_ENABLED=1, REPOTOOLS_BETA_DB_ISOLATED=1, APP_URL de beta, REFERRALS_DB_HOST del endpoint aislado y REFERRALS_SIGNAL_KEY de al menos32caracteres. Directo y pooled del mismo endpoint son compatibles. En producción, origen distinto, flags ausentes o host que no coincide, el sistema se mantiene desactivado y el registro tradicional no consulta las tablas nuevas. No se ejecutan migraciones desde autenticación.

## Datos y migración
`php scripts/migrate-referrals.php` es explícito/CLI e idempotente, con transacción/mutex PostgreSQL. Se añadieron6tablas: referral_codes (PKcuenta/código único aleatorio permanente), referrals (invitado único, referente/invitado FKdistintos, estado y timestamps), referral_decisions (auditoría), referral_verifications (hash de token y vencimiento), referral_limits y referral_mutex. Índices para períodos, referente, revisión y retención. Constraint de validación exige correo confirmado y fecha, y estado no validado exige fecha nula. Sin cambio del esquema de usuarios ni backfill de referencias retroactivas.

## Atribución, correo y fraude
Código aleatorio12caracteres,48bits, sin datos privados; se genera al abrir la sección y se conserva. Ruta `/r/CODIGO` → invitar.php → formulario normal. Último enlace válido queda en sesión hasta7días; código manual tiene prioridad. No nuevo identificador oculto ni cookie adicional. Registro normal/incorrecto continúa sin atribución. Asociación se inserta únicamente al crear cuenta, en la misma transacción; invitado único/no autorreferido/normalización del correo/control de existentes evitan dobles referentes.

El registro actual no verificaba correo. Solo las cuentas nuevas atribuidas reciben el nuevo desafío; las cuentas tradicionales conservan su comportamiento. Pendiente hasta confirmar mediante token aleatorio256bits con hash,24h, consumo atómico y POST+CSRF para que un previsualizador de correo no valide automáticamente. Varios tokens/eventos no multiplican el crédito. Verificación liga la prueba al correo actual. La cuenta puede usar la aplicación mientras el referido está pendiente; no se pide cargar productos ni palets.

Envío con Resend/MAIL_FROM existentes y botones del color#27187e. Registro queda guardado aunque falle el envío; se puede reenviar desde Referidos, máximo3/hora. No se afirma entrega real de correo por las pruebas automáticas: proveedor se dejó sin credenciales en tests.

Señal de IP mediante HMAC con secreto del entorno; no IP cruda ni fingerprinting invasivo. No se confía en X-Forwarded-For salvo que REMOTE_ADDR pertenezca a REFERRALS_TRUSTED_PROXIES explícito; se toma la primera dirección no confiada desde la derecha. Sin configuración se utiliza el peer, lo cual puede agrupar solicitudes detrás de un proxy: señal débil, revisión humana, nunca rechazo/bloqueo automático por IP compartida. Ocho registros anteriores en15min o honeypot marcan revisión. Correo y revisión humana son el desafío adicional; no se instaló CAPTCHA externo ni se promete identificar toda cuenta fraudulenta. Límites de captura/registro/verificación por sesión y correo por cuenta, sin bloquear a trabajadores solo por compartir Wi-Fi. Señales se purgan tras30días al usar el sistema; tokens/contadores vencidos se limpian. Auditoría de decisiones y relación de invitación se conservan para ranking e integridad. Revisar la política de privacidad pública antes de generalizar fuera de beta; no se localizó una política publicada en el repositorio.

## Ranking y administración
Ranking semanal lunes00:00–lunes siguiente exclusivo, mensual primero–primero siguiente exclusivo e histórico. Zona America/Argentina/Buenos_Aires, instantes epochUTC. Cuenta solo estado validated y fecha de validación. Orden: totalDESC, fecha en que alcanzó el totalASC (MAX de validaciones del período), ID como último desempate interno. API pública devuelve posición, alias público y total; no correos, IP, invitados ni IDs internos. Paginación50; posición propia incluso fuera de página; fecha permite períodos anteriores. Sin datos: estado vacío. Estadísticas propias: código/enlace,4estados y3posiciones; invitados privados no se listan innecesariamente.

`referidos.php?admin=1` / `api/referrals.php?admin=1`: administradores/managers revalidados desdeDB. Filtros estado/fechas/referente;25porpágina; fechas/riesgo/motivo/historial de últimas50decisiones por ticket. Aprobar requiere correo confirmado; motivo3–300caracteres obligatorio para toda decisión, incluido rechazo. Solo manager revierte validado/rechazado; administrador no decide sus propias invitaciones. Manager conserva facultades completas. Mutex/transacción/revisión protege decisiones simultáneas; agregación por fila evita sumar dos veces. Revalidar tras rechazo usa la fecha de nueva validación, de forma consistente con los períodos. Historial identifica actor/fecha/estado anterior/nuevo/motivo.
